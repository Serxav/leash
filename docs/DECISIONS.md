# Decision log

Every important technical decision, in plain words, so Sergi can explain each part of the
project. Newest at the bottom.

**Format.** Each entry has an ID and a date, then:
- **Decision:** what we chose.
- **Alternatives:** what else we considered.
- **Why:** the reason.
- **Status:** accepted, pending or replaced.

### D-001 · 2026-10-14 · Repository protection from day one

- **Decision:** public repo `Serxav/leash` with the MIT licence and the Node `.gitignore`.
  - `.claude/settings.json` denies Claude Code read/edit access to `.env` and `.env.local`,
    and is the only direct commit to `main`.
  - A ruleset on `main` blocks deletion and force pushes, and requires a pull request
    (0 approvals) and linear history, with no bypass actors.
  - Only squash merge is allowed, and branches are deleted on merge.
  - Secret scanning, push protection and Dependabot alerts are enabled.
- **Alternatives:** classic branch protection; protecting `main` later.
- **Why:** the hackathon rejects leaked secrets and broken demos, and every change should
  pass CI before reaching `main`. Rulesets are GitHub's current mechanism and also block
  admins.
- **Status:** accepted. Follow-up done: both CI checks ("Lint, typecheck, test, build" and
  "Secret scan (gitleaks)") are required status checks, with the strict policy.

### D-012 · 2026-10-15 · CI design

- **Decision:** one GitHub Actions workflow (`.github/workflows/ci.yml`) that runs on every
  pull request and on every push to `main`. It has two jobs:
  - **Lint, typecheck, test, build:** `npm ci` on the Node version read from `.nvmrc`.
  - **Secret scan (gitleaks):** scans the whole git history with the gitleaks 8.30.1
    binary. The binary is downloaded from the official release and checked against its
    published SHA-256 before running. It is not the gitleaks GitHub Action.

  Other choices:
  - Third-party actions are pinned to full commit SHAs, with the version in a comment.
  - The token is read-only (`contents: read`), and the checkout does not keep git
    credentials.
  - The CI has no secrets. Sandbox integration tests stay local
    (`npm run test:sandbox`).
- **Alternatives:** the gitleaks GitHub Action; actions pinned by tag only.
- **Why:**
  - The brief says to use the gitleaks binary if the action needs a licence. The binary
    never does, and pinning plus a checksum makes the scan reproducible.
  - Pinning actions by SHA protects against a compromised tag (supply-chain safety).
  - Both job names become required status checks on `main`.
- **Status:** accepted.

### D-013 · 2026-10-15 · Own server-side PayPal OAuth client (REST)

- **Decision:** `src/paypal/auth.ts` gets OAuth tokens over plain REST
  (`POST /v1/oauth2/token`, client credentials), following
  https://developer.paypal.com/api/rest/authentication/.
  - It refuses any host but the sandbox API **before** sending anything.
  - It caches one token per process and renews it 60 s before expiry. Concurrent callers
    share one request, and errors are not cached.
  - Errors keep the HTTP status, PayPal's error code and the `paypal-debug-id`, never
    credentials.
- **Alternatives:** `@paypal/paypal-server-sdk`, which also handles OAuth.
- **Why:** F0 findings that shape F1:
  - The official PayPal Server SDK **is generated with APIMatic**: its dependencies are
    `@apimatic/*`. Using it for Orders/Payments may count as using APIMatic tools (D-007).
    Decide in F1.
  - Its README says its **Vault controller is "Available in the US only"**. The Vault
    *API* itself supports Spain: "Save PayPal for purchase later" lists Spain among the
    supported countries. So vault calls (`/v3/vault/setup-tokens`,
    `/v3/vault/payment-tokens`) will likely be direct REST, and they need our own token
    anyway.
  - The vault docs say PayPal **requires Risk Data Acquisition (RDA)** with the FraudNet
    and Magnes libraries. This must be planned in F1.
  - The vault docs show `usage_type` both as `PLATFORM` (step text) and as `MERCHANT`
    (sample request). Leash is a single merchant, so we use `MERCHANT`. Confirm in F1.
- **Status:** accepted. Sandbox test: a real token with the vault and reporting scopes, and
  401 on wrong credentials.

### D-014 · 2026-10-15 · Agent Toolkit vs Vercel AI SDK (spike result)

- **Finding:** `@paypal/agent-toolkit` 1.11.0 (latest, published Sep 29, 2026) depends on
  `ai ^4` and `zod ^3` as **hard dependencies**. Its `./ai-sdk` export builds AI SDK v4
  tools. Our stack is `ai` 7 and `zod` 4, so its tools cannot be passed straight to the
  model. It also pulls in `openai`, `@langchain/core`, `mathjs` and `@dotenvx/dotenvx`.
- **Decision for F3:** define each leashed tool ourselves with `ai` v7 `tool()` and our own

  `execute`. The toolkit still runs the real PayPal calls. Only the read-only tools (order
  and transaction status) and refund-with-confirmation are exposed.
- **Alternatives:**
  - Downgrade `ai` to v4: too old for current Claude models.
  - Run the toolkit as an in-process MCP server through the AI SDK MCP client: more moving
    parts.
- **Status:** accepted direction. Installing the toolkit (large dependency) will be asked
  for in F3.

### D-016 · 2026-10-15 · PayPal Server SDK (APIMatic) built with the APIMatic Context Plugin

- **Decision:** use the official **PayPal Server SDK** (`@paypal/paypal-server-sdk`,
  pinned to `2.5.0`, generated by APIMatic) for Vault, Orders and Payments. Build it with
  the **APIMatic Context Plugin for PayPal**, installed in Claude Code from
  `paypaldev/server-sdk-context-plugin-preview` at commit `6aa0571`. The installer's
  telemetry is off, and the plugin is skills only (no hooks or MCP).
- **Why:**
  - The APIMatic sponsor prize is for teams that **used the Context Plugin** to build their
    PayPal integration (checked on the Devpost APIMatic page).
  - The plugin's TypeScript skills were followed step by step:
    - one long-lived client;
    - `clientCredentialsAuthCredentials` with `oAuthClockSkew: 60`;
    - an explicit 30 s timeout, because the SDK has none by default;
    - the default `NullLogger`, so tokens are never logged;
    - the default retries, which never retry POST, so no duplicate charges;
    - the error-handling trap: `OAuthProviderError` is shadowed by a same-named model, so
      it is never used with `instanceof`;
    - stubbing through `unstable_httpClientOptions.adapter` with a seeded token in tests.
- **Vault in Spain:** the SDK README says its Vault controller is "US only". Tested in the
  sandbox with our Spanish accounts, `VaultController.createSetupToken` returned 201
  `PAYER_ACTION_REQUIRED`, and the full approval → payment token flow works. So no
  separate REST client is needed for the vault (D-013's fallback is not used).
- **Mandate settings:**
  - `usage_type: MERCHANT`: the Leash Demo Store charges.
  - `customer_type: CONSUMER`.
  - `usage_pattern: IMMEDIATE`: variable amounts at variable times.
  - `permit_multiple_payment_tokens: false`.
  - `shipping_preference: NO_SHIPPING`: no addresses are ever collected or stored.
  - Every call uses a `PayPal-Request-Id` derived from our own mandate ID.
- **Safety checks:**
  - The approval link must be `https://www.sandbox.paypal.com`.
  - On return, Leash exchanges the setup token **it stored**. PayPal's
    `approval_token_id` is only checked to match.
  - The UI view never includes the vault token.
- **Known issue:** `npm audit` now also lists 4 moderate findings in `drizzle-kit`'s old
  `esbuild`. It is a dev-only migration CLI, never deployed.
- **Status:** accepted. US1 was verified end to end in the sandbox on 2026-10-15: Personal
  account (ES), approval on www.sandbox.paypal.com, mandate `ACTIVE`.

### D-018 · 2026-10-15 · Charging the mandate (Orders v2) with FraudNet risk data

- **Decision:** `src/payments/charge.ts` charges the mandate with one Orders v2 order:
  intent `CAPTURE`, `payment_source.paypal.vault_id`, EUR only. PayPal captures it
  immediately.
- **Idempotency:** each attempt is written to `payments` **before** calling PayPal, and
  its id is used for three things:
  - `PayPal-Request-Id`;
  - `invoice_id`, which must be unique, so a second charge is rejected as
    `DUPLICATE_INVOICE_ID`;
  - `custom_id`.

  If the outcome is unknown (network or timeout), the row stays `PENDING` and is never
  assumed to be uncharged.
- **Who initiates:** `payment_source.paypal.stored_credential.payment_initiator` is:
  - `CUSTOMER` when the user is present (one-tap approval, the lab button);
  - `MERCHANT` when the agent buys within the rules without the user.

  `usage_pattern: IMMEDIATE` matches the mandate.
- **Risk data (RDA):** PayPal requires it for customer-initiated payments with PayPal
  payment tokens.
  - Every page that can start one renders FraudNet (`src/components/fraudnet.tsx`) with a
    new 32-character session id. `s` is `<PAYPAL_MERCHANT_ID>_<page_id>` and
    `sandbox: true` is set.
  - The same id is sent as `PayPal-Client-Metadata-Id`.
  - A `CUSTOMER` charge without a valid id is refused before calling PayPal.
  - `PAYPAL_MERCHANT_ID` is the public Merchant ID of the sandbox Business account (a new
    optional variable, format-checked at startup). It was read from an unapproved,
    never-charged order's `payee.merchant_id`.
- **FraudNet loading:** `fb.js` is a plain `<script async>`, PayPal's documented
  "option 1", not `next/script`. With `next/script` inside a `<Suspense>` boundary, the
  script was only preloaded and never ran until that boundary hydrated. With a plain tag,
  the browser runs it straight from the streamed HTML. Verified in the browser: `fb.js`
  loads and sends data to `c.sandbox.paypal.com`.
- **Return window:** COMPLETED payments get `withdrawal_deadline` = capture time + 14 days
  (D-008).
- **Status:** accepted. Verified in the sandbox on 2026-10-15:
  - a €5.00 CUSTOMER charge, capture `1GM787476M628661F`. The Payments API confirms
    COMPLETED, 5.00 EUR, payee = the Business merchant, €4.48 net, seller protection
    ELIGIBLE;
  - a €1.00 MERCHANT charge without risk data, also COMPLETED (sandbox test).

### D-019 · 2026-10-15 · Refunds (Payments v2)

- **What:** `src/payments/refund.ts` refunds a completed payment in full with
  `PaymentsController.refundCapturedPayment` (POST `/v2/payments/captures/{id}/refund`).
  The body is empty, which PayPal documents as a full refund.
- **Why only full refunds:** the user returns the whole purchase within the 14-day window
  (D-008). Partial refunds add amount checks and states the MVP does not need.
- **Idempotency:** the `PayPal-Request-Id` is `refund-<paymentId>`, derived from the
  payment. A double click or a retry after a timeout gets the same refund back, never a
  second one. A payment already `REFUNDED` in Leash is not sent to PayPal again.
- **Who can refund:** only the payment's owner, only when it is `COMPLETED` and has a
  capture. Anything else is refused before calling PayPal.
- **PayPal answers** (issue names checked in the official Payments v2 spec):
  - refund `COMPLETED` → payment `REFUNDED`, `refundId` saved;
  - refund `PENDING` → payment stays `COMPLETED` with its `refundId`, shown as
    "refund pending";
  - `CAPTURE_FULLY_REFUNDED` (already refunded, for example from the PayPal dashboard) →
    Leash marks the payment `REFUNDED` instead of failing;
  - any other error (`REFUND_AMOUNT_EXCEEDED`, `REFUND_TIME_LIMIT_EXCEEDED`,
    `TRANSACTION_DISPUTED`…) leaves the payment unchanged and shows the issue and
    `debug_id`.
- **Status:** accepted. Verified in the sandbox on 2026-10-15:
  - the €5.00 capture `1GM787476M628661F` refunded from the lab button (refund
    `72C560913E260084A`);
  - sandbox test: €1.00 charge → refund → a second refund with a new request id is
    rejected with `CAPTURE_FULLY_REFUNDED`.

### D-020 · 2026-10-15 · Declined payments and user messages

- **How a decline is reproduced:** PayPal sandbox negative testing. The charge accepts an
  optional `sandboxMockIssue`; when set, Leash sends the `PayPal-Mock-Response` header
  `{"mock_application_codes":"INSTRUMENT_DECLINED"}` on create order, and the sandbox
  answers with that error instead of charging.
  Docs: https://developer.paypal.com/tools/sandbox/negative-testing/request-headers/
- **Why an allowlist:** only `INSTRUMENT_DECLINED` is accepted (`SANDBOX_MOCK_ISSUES`), so a
  form field can never inject an arbitrary header value. Leash never runs outside the
  sandbox (startup guard), so the option cannot touch real money.
- **Handling** (already in D-018): Leash branches on `details[0].issue`. `INSTRUMENT_DECLINED`
  → payment `DECLINED`; anything else → `FAILED`. The issue and `debug_id` are kept.
- **User messages:** `src/payments/messages.ts` turns each issue into one plain sentence:
  what happened, whether money moved and what to do. The issue code and debug ID are shown
  below it, for support.
  - An unknown issue, a network error or a timeout never says "nothing was charged": the
    outcome may still be unknown. It says to check the payment history before retrying.
  - Only the module's own keys are read (`Object.hasOwn`), because the issue can come from
    a URL.
- **Status:** accepted. Verified in the sandbox on 2026-10-15: the lab's "Simulate a
  declined €5.00 charge" button got `INSTRUMENT_DECLINED` from PayPal (debug ID
  `70c28ae654da`), recorded the payment as `DECLINED` and showed the message. The sandbox
  test does the same with a €1.00 merchant-initiated charge.

### D-021 · 2026-10-15 · Spending rules schema (Zod)

- **What:** `src/rules/schema.ts` defines the user's confirmed rules. Fields, all required:
  - `formatVersion` (1) and `currency` (`EUR` only);
  - `maxPerOrder` and `monthlyBudget`: hard limits, inclusive;
  - `approvalThreshold`: orders **above** it need approval (an order of exactly this
    amount does not: "ask me before anything over €15"); `null` means no approval step;
  - `allowedCategories`: 1–20 catalog category slugs (Channel3 slugs, D-015);
  - `blockedMerchants`: 0–50 hostnames;
  - `maxUnitsPerItem`: 1–100, inclusive.
- **Money:** euro amounts are strings with two decimals ("40.00"), the same format PayPal
  uses, and every comparison is done in integer cents (`src/lib/money.ts`), never with
  floats or text. The charge now uses the same helper.
- **Security, because rules can come from an AI model:**
  - strict object: unknown fields are rejected, so neither the model nor injected text can
    add something like `allowEverything`;
  - no silent defaults and no "no limit" value: every limit must be set, and amounts are
    capped at €10,000.00;
  - categories and merchants are closed formats (slugs and hostnames), never free text
    that could carry instructions. Merchant URLs are normalised
    (`https://www.Shop.example/x` → `shop.example`); anything else is rejected;
  - consistency checks: `maxPerOrder` ≤ `monthlyBudget` and
    `approvalThreshold` ≤ `maxPerOrder`;
  - validation problems name the field and the reason, but never echo the rejected value
    or unknown key names, which could be injected text;
  - checked against oversized and ReDoS-style inputs (100,000 characters): under 2 ms.
- **For the engine (next task):** blocked merchants also block their subdomains, and
  catalog categories are compared after the same normalisation (trim + lowercase).
- **For the rules builder:** the schema exports as a strict JSON Schema
  (`additionalProperties: false`, all fields required), usable for structured AI output.
- **Rule IDs:** `RULE_IDS` lists the stable IDs in the brief's evaluation order (state →
  hard blocks → approval threshold). Decisions store them.
- **Status:** accepted.

### D-022 · 2026-10-15 · The policy engine

- **What:** `decide(rules, request, state)` in `src/rules/engine.ts` returns `APPROVE`,
  `NEEDS_APPROVAL` or `BLOCK`, the IDs of the rules that decided it, a one-sentence
  explanation and the order total. It is plain TypeScript: no AI, no network, no clock of
  its own (the caller passes `now`), so the same input always gives the same decision.
- **Order** (brief §4):
  1. input check (`valid_request`);
  2. state: an `ACTIVE` mandate (`mandate_active`) and an agent that is not paused
     (`agent_active`). These stop the check: nothing else matters;
  3. hard blocks, all collected in order: category, merchant, units, limit per order,
     monthly budget. The explanation gives the first one and how many more;
  4. approval threshold: strictly above it → `NEEDS_APPROVAL`;
  5. approve.
- **Semantics:** every limit is inclusive (an order of exactly €40.00 with a €40.00 limit
  is allowed; exactly the threshold does not ask). Blocked merchants also block their
  subdomains, but never look-alikes (`notshop.example`, `shop.example.evil.example`).
  Categories match exactly after the same normalisation as the rules.
- **Monthly budget:** the caller passes the purchases that count (`countsTowardBudget`:
  `COMPLETED`, `PENDING`, `PARTIALLY_REFUNDED`; `PENDING` counts because the money may
  have moved). The engine keeps those in the current calendar month in Europe/Madrid
  (`Intl` with the `Europe/Madrid` time zone, so summer and winter time are handled).
  All sums are in integer cents.
- **Fails closed (security review):**
  - the rules are validated again (they may come from the database); invalid or tampered
    rules block everything;
  - each input is read once and its real type is checked, with no coercion: an object

### D-024 · 2026-10-15 · Rules builder: the AI extracts, the code decides

- **What:** `buildRules({ model }, text)` in `src/rules/builder.ts` turns the user's plain
  language into exact rules, or into questions. Nothing applies until the user confirms
  the result (next task).
- **Two steps:**
  1. **The model extracts** a loose draft with structured output (`Output.object`):
     amounts as written, `null` for anything not mentioned, `"none"` for "never ask me",
     category slugs, domains, and questions about anything ambiguous.
  2. **The code decides** (`completeDraft`, no AI): it reads amounts as people write them
     (`40`, `40,5`, `€40`, `40 €` → `"40.00"`; anything else is asked again), turns
     categories into slugs, sets `currency: "EUR"` and `formatVersion` itself, copies only
     known fields, and validates the result with the strict rules schema (D-021).
- **Asks instead of guessing (US2):** a missing or unreadable value becomes a fixed,
  plain question from the code. The model's own questions about ambiguity (for example
  "What is the website domain for Marketplace X?") are shown once nothing is missing, so
  the user is never asked the same thing twice. Other currencies are refused (Leash never
  converts). At most 5 questions, each cleaned and capped at 200 characters.
- **Security review:**
  - the model has no tools, runs at temperature 0 with a 30 s timeout, and only sees the
    rule text (no user data);
  - the user's text is capped at 1,000 characters and sent as delimited data after the
    instructions; the user cannot close or reopen the data block;
  - the model never writes the final rules: invented fields (`allowEverything`) and its
    own `formatVersion` or currency are ignored, and everything goes through the strict
    schema;
  - problems never echo invalid values; provider error details are never shown (they can
    carry request details);
  - model questions are plain text, shown through React, which escapes them.
- **Live check with `gemini-3.1-flash-lite`** (invented data): the brief's example gives
  exactly the expected rules; a Spanish example ("nunca me preguntes", "papelería y
  limpieza") gives `approvalThreshold: null` and `stationery`, `cleaning-supplies`; vague
  text gives the four missing-value questions; an injection attempt gives questions, never
  silent rules.
- **For later:**
  - F3: category slugs are free English slugs; the catalog's Channel3 categories must be
    mapped to the same slugs, or the engine blocks them (it fails closed);
  - F5: the rules builder calls a paid model in the public demo, so its route needs the
    same per-visitor rate limit as the agent routes.
- **Status:** accepted.

### D-025 · 2026-10-16 · No key can leak: layers of protection

- **Why:** the repository is public, so any key that reaches it is leaked for good. The
  official rules ask for a way to test the project ("test account credentials, API keys,
  or sandbox login details"), not for our keys: judges get the hosted demo plus the
  sandbox Personal login, or instructions to run it locally with their own free keys.
- **Layers, from the disk to the browser:**
  1. **Disk:** keys live only in `.env.local`, ignored by git; `.env.example` has names, no
     values. The SQLite files (which hold vault tokens) and `data/` are ignored too (#14).
     Claude Code is denied read and edit access to `.env` and `.env.local`.
  2. **GitHub:** secret scanning and push protection are on; CI runs gitleaks on every pull
     request and both checks are required to merge. The whole history was scanned on
     Oct 16: no secrets.
  3. **Server only:** only `src/config/env.ts` reads `process.env`. It, the PayPal OAuth
     client, the PayPal SDK client, the database client and the AI models file import
     `server-only`, so importing any of them from browser code fails the build (tested on
     Oct 16 with a throwaway client component: the build failed). There are no
     `NEXT_PUBLIC_` variables and no client components yet.
  4. **Browser output:** on Oct 16, the 49 files Next.js serves to browsers (`.next/static`
     and the prerendered pages) were searched for the real value of every key and for key
     patterns (Google, Anthropic, PayPal access tokens): none found. The script printed
     only names and found/not found, never a value.
  5. **Logs and errors:** env validation names variables but never their values; PayPal and
     AI provider errors are reduced to an issue code and a debug ID; nothing logs requests,
     headers or tokens.
  6. **The model:** it only ever sees rule text (and later, public product data); no
     credentials, tokens, emails or internal PayPal IDs (CLAUDE.md).
- **Tests:** Vitest maps `server-only` to an empty stub (`tests/stubs/server-only.ts`), so
  unit and sandbox tests import the guarded files normally.
- **Status:** accepted. Repeat the browser-output scan before the submission (F6).
